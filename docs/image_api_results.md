# 图片模型配置与执行结果

## 模型配置

- 图片工作流读取独立的 `image_model`，不再使用文本模型 `baseline_model`。
- 优先级：云端非空配置 > 本机非空配置 > `gpt-image-2` 兼容默认值。
- 设置页面分别提供图片模型、文本模型；整图海报、文生背景、图片编辑均通过 `--model` 传给 Images API，并写入请求包和生成记录。
- 自定义模型需兼容当前 Images API 请求参数（包括尺寸、质量和编辑上传格式）；修改名称不代表获得模型权限。
- “检查图片模型”仅 GET `/models`，不出图、不自动重试。模型列出不保证生成/编辑可用，未列出也不能单独证明不可用。

## 结果约定

| `status.json` 的 `result.outcome` | 退出码 | 含义 |
| --- | --- | --- |
| `prepared` | 0 | 仅准备请求包，未调用图像 API |
| `success` | 0 | 所有要求的生成及后处理阶段成功 |
| `failed` | 1 | 没有可用生成结果 |
| `partial` | 3 | 部分候选成功，或已有主图但后处理失败 |
| `needs_input` | 4 | 图片编辑 Agent 需要澄清，尚未调用图片模型 |
| `cancelled` | 130 | 捕获到取消；上游请求可能仍在执行 |

参数校验错误使用退出码 2。初始化或不可恢复异常可能在结果包建立前退出；GUI 不会将缺少有效结果的图片任务判为成功。

`result` 同时含 `completed`、`total`、`message` 和 `exit_code`。计数以候选为单位，只有该候选全部要求阶段完成才计为完成。`DASHDESIGN_PROGRESS=1` 时，stdout 发送同内容的 `result` 事件，再由 GUI 联合进程退出状态判断；仅有退出码 0 不够。

阶段结束后原子更新 `status.json`。同名请求包使用后缀隔离，避免误认旧图片；文件必须通过图片解码验证才能记为生成成功。部分成功保留工程包，不自动整理为完整成品。错误记录保留 HTTP 状态、模型、错误类别、请求 ID 与脱敏摘要，不保存原始响应体、Key 或签名下载 URL。

SIGTERM 在可捕获的图片/后处理调用期间转换为取消。强制 kill、Windows 强制终止或磁盘故障可能使最终结果无法落盘，此时保留最后检查点；GUI 的用户取消标志独立生效。超时/连接中断和图片下载失败可能发生在上游已出图之后，不能据此判定未扣费，因此不自动重发请求。

## 升级与验收

图片修改的多模态语义转写、独立 `edit_agent_model` 配置和澄清续跑见 [图片修改语义 Agent](image_edit_agent.md)。

1. 先升级云端，再升级桌面端。云端写入合并显式提供的字段，旧客户端不提交 `image_model` 时不会覆盖已配置值；JSON 配置存储无需新增数据库列。
2. 管理员填写实际获授权的图片模型。云端配置仍按现有启动刷新机制分发。
3. 用模拟 HTTP 和小图片回归生成、编辑、404、鉴权、限流、超时、空响应、下载/解码失败、部分成功与 GUI 状态；隔离 QSettings，不调用真实上游。
4. 发布安装包后仍需分别验收 macOS/Windows worker、设置页面及真实授权模型出图。本次代码修复不能代替上游分组/渠道绑定修复。
